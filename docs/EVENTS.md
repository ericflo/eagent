# The event log

Every session is a directory of JSONL files under `.agents/eagent/sessions/`.
Each line is one event:

```json
{"seq":14,"ts":"2026-09-07T01:54:03.120Z","type":"assistant","actor":"eagent","data":{...}}
```

| Field | Meaning |
|---|---|
| `seq` | Monotonic within the session, across subsession files. Never reused. |
| `ts` | UTC time the event was appended. |
| `type` | One of the types below. Dotted, stable; new types may be added, existing ones are never renamed. |
| `actor` | `user`, `harness`, `eagent`, or `summarizer`. Older logs also name `orchestrator`, `task` and `narrator` (see *Events in older logs*). |
| `task` | Set only in older logs, on task-worker events (`t3`). |
| `data` | Type-specific payload. |

Lines are appended with `fsync`. Committed lines are never edited. A crash
mid-write leaves a final line without a newline; readers skip it, and the
next writer moves those bytes to `<file>.torn` before appending.

eagent is the one model-driven actor. Some type names come from when a
separate narrator did the talking: `narrator.message`, `narrator.question`
and `narrator.checks` keep those names, and their actor is `eagent`.

What wakes eagent's model is decided by `wakeFor` (`internal/harness/loop.go`).
A wake waits 400 ms for events that arrive together, then makes one call that
answers all of them. The notes below say which events wake it.

## Types

### Session lifecycle

| Type | Actor | Payload | Notes |
|---|---|---|---|
| `session.start` | harness | `session`, `cwd`, `version`, `interactive`, `models{actor: model}`, `endpoints{actor: base_url}`, `efforts{actor: effort}`, `config`, `tz`, `phone_ledger` | First event of a session. The maps name the routes actually in use (a fallback may have taken over at startup): `eagent`, plus `summarizer` when the summarizer is dedicated. `config` names the bundle or preset. `tz` is the IANA zone clock times are rendered in for the model, fixed for the session's life. `phone_ledger` says this run records every app message it takes in (see `phone.read`). |
| `session.resume` | harness | `interactive`, `closed[]`, `phone_ledger`, `after` | Appended when a session is resumed. `closed` lists the agents that were gone when it reattached. Wakes eagent when `closed` is not empty. `phone_ledger` says this run records every app message it takes in (see `phone.read`); a run by an eagent without it leaves it out, and its record is then read by time. `after` is the seq of the newest event the record held when this run opened it: a resume closes a cut turn before it writes this event, so `after` is where the run before stopped. In a log of the three-actor design, the first one with `phone_ledger` marks where the one loop took over: nothing up to its `after` is owed a look, and what came after it is, as in any log. |
| `session.end` | harness | `reason` | `done`, `awaiting-input`, `quit`, `interrupted`, `error`. A session can be resumed after any of these. A send never typed (held for a start the end cut short, still queued behind another, or still waiting for the agent when the end closed its terminal) gets its `relay.delivered` (`not_sent`) first, stamped with its relay's last event time so a reattach still reads what the agent did after that; one whose typing began keeps what its typing gives. Silent looks not yet counted are written as a `narrator.checks` first. The agents keep running in their terminals for a resume to pick up, except after Stop session, which writes a `relay.end` for each first. |
| `subsession.start` | harness | `file`, `index`, `reason` (`new`, `rollover`, or `upgrade`) | First event in every file. `upgrade` opens the first subsession an older log gets when it is resumed. |
| `subsession.end` | harness | `reason` (`context full`, or `resumed by an eagent with one loop`), `next_file`, `input_tokens` | Last event in a file that rolled over. `input_tokens` is the prompt size that triggered it. |
| `dossier` | harness | `text`, `covers_seq`, `covers_none`, `by` (`eagent` or `harness`), `no_map`, `usage`, `elapsed_ms`, `calls`, `consulted[]`, `host`, `asked`, `earlier[]` (`host`, `asked`, `usage`, `calls`), `restart` (`carried`, `retried`, `rescues`), `task_id` (older logs) | The briefing that opens a rolled-over subsession: where the session stands and a map (`file:line`) of where each topic can be read, followed by facts the harness adds from the log. `covers_seq` is the last event it took in. `covers_none` says it took in none (the session's first request was refused as too long, so no call had seen anything); a log with neither field is an older one that does not say. `by: harness` means the model could not write it and the harness built it from the log. `no_map` marks a body by the model that was kept although it cites too few places to be a map (it was sent back once and came back the same); the body says so in its first lines. `consulted` lists the lookups the writer made (`read FILE:40-90`, `search deploy`); the lookups themselves are not recorded. Its usage counts toward eagent's, priced on the route `host` and `asked` name; when the model changed during the pass, `earlier` holds the calls another route served before, each priced on its own, `usage` is the last route's alone and `calls` still counts them all. A record without them is priced on the route in use. `restart` is how this restart stands in a run of restarts: `carried` says it carried whole what no look had taken in, `retried` that it was the one more try after a restart that carried nothing and was refused, and `rescues` how many restarts in a row, this one included, were made for conversations too long from their start. A resumed run reads them from the dossier that opens the conversation in use, so it stops the restarts where the stopped run would have; a move to another model after that dossier starts `retried` and `rescues` again, as a move in a running session does. A dossier without `restart` (older logs) leaves all three unknown. |
| `cwd.change` | harness | `path`, `previous` | The folder the session works in, written at start when it is not the project root (`--cwd`, or `cwd` on a phone `session.start`). Agents start there unless told otherwise. Mirrored to the phone as the thread's folder and branch chips. |

### Conversation

| Type | Actor | Payload | Notes |
|---|---|---|---|
| `user.message` | user | `text`, `source` (`web`, `finalechat`, or absent for the terminal), `client` (optional capsule of what the sending client declared it can supply: `source`, `timezone`, `locale`, `device`, `app`, `screen`, `supplies`), `attachments` (files saved under `<session>/attachments/`: `path`, `name`, `content_type`, `size`, `kind`, `width`, `height`, `id`), `route` (`agent` or `eagent`, when the client let the user say whom it is for), `delivery` (`queue`, `interrupt`, `after_turn`), `held`, `phone_id` (the FinaleChat message id), `card_id` (the phone card whose answer these words are, when a card's answer was kept as a message because its question was settled another way), `inbox` (the name, without `.json`, of the `<session>/inbox/` file the words came in, when the file gives that name as its `inbox_id`, as every file `eagent serve` writes does; a file that does not (one written by hand) is first moved to a new name of eagent's and written again there with that name as its `inbox_id`; absent when that could not be done) | Wakes eagent. Unless `held` is set, the harness types it into the agent's terminal as it arrives, word for word, before any model call (a `relay.send` with `from: user`, `auto: true`). When the record ends at such a message (eagent stopped before its `relay.send` was written, so nothing of it was typed), the resume routes it again and, unless that keeps it, sends it then, before its `session.resume`; one kept (no send of it by then, the `session.resume`'s `after` naming it) shows on the phone as kept for eagent. `held` says why it was kept for eagent instead: it was addressed to eagent, no agent or more than one is running, the agent is not running, or it asks about the session. eagent then answers it or passes it on with `relay_forward`. |
| `user.answer` | user | `question_id`, `text`, `source`, `client`, `attachments`, `phone_id` (the FinaleChat message it came in, when it came from the phone), `card_id` (the phone card it was written on, when it was), `inbox` (as on `user.message`) | What the user wrote while a `narrator.question` was open; an option's number is recorded as the option's text. Wakes eagent. `phone_id` and `card_id` put the answer in the session's ledger of app messages taken in (see `phone.read`) in the one write that records it. An inbox file is removed only after the `user.message` or `user.answer` it became is written; a file still in the inbox that this run took, or that was there when the run took the session and that some `user.message` or `user.answer`'s `inbox` names, is removed without being taken again. |
| `user.dismiss` | user | `question_id`, `source` | The user closed a `narrator.question` without answering (Dismiss on the phone card, the button in the web UI, or `/dismiss`). The question is over and nothing was decided. It wakes nobody; eagent reads that it was dismissed with whatever wakes it next. `ask_user` is refused until the user writes or an agent finishes a turn, blocks or exits. A card dismissed while the session was not running is recorded when the session resumes, before the resuming message, so that message is not taken for the answer. |
| `turn.start` / `turn.end` | eagent | `reason` | Bracket a turn that went on the record. `turn.start` is written when a call first acts, with the wake's reason; `turn.end` gives `done`, `call limit`, `error`, `interrupted`, `error, closing` (a call of the closing turn failed after the closing word, the model's report or eagent's own, went out, or a call of the last title and summary of a session that is ending failed, which is one attempt; unlike `error`, nothing is owed after it), or `not closing` (a closing turn, the closing word's or the last title and summary's, whose session stopped ending, as eagent's own end of the session has it: an agent was started, a timer set, a question asked on the phone, a command is still at work, the user dismissed a question and has its time to write instead, or the user wrote; it ends after the call that made it so, where it would have made another call or could not finish that call's tools in its own time). A look that ends in silence writes neither. An `error` end (the turn acted, asked for another call, and that call failed) wakes eagent: the call is still owed, and is made when the failure lets it (after the retry's wait, after the restart a refusal as too long sets off, or in a resumed run), on the record as it stands. A `not closing` end wakes eagent the same way: the call is owed, and an ordinary turn makes it, with its own time limit and reminders. |
| `steer` | eagent | `text` | The tail of the prompt for a look eagent acted on: why it was woken, what each agent is doing right now, the steps an agent took since the user last heard, how long that has been, what is expected of the reply. Written right before the `assistant` event it led to. A look that ends in silence leaves no steer. |
| `assistant` | eagent | `provider`, `model`, `asked`, `host`, `text`, `reasoning`, `tool_calls[{id,name,args}]`, `native`, `usage{input,output,cached,reasoning}`, `elapsed_ms`, `seen_seq`, `stop` | One model response that acted (called a tool other than `hold`). `native` is the provider's own representation (Responses output items, Anthropic content blocks), replayed verbatim on later calls to the same `host` (on Responses, only to the same `model`, a dated variant included; on Anthropic, a turn another vendor's model wrote is rebuilt for Claude). `model` is the model the response named and `asked` the one the request asked for (absent in older records, which are held to `model`): `asked` says which route served the call and which model the native items can go back to; a reply from a route that is no longer the one in use (it was still out when the model changed) is priced there and does not set the conversation's size. `reasoning` is a summary for humans, clipped to 4000 characters. `seen_seq` is the last event the prompt contained; anything after it is delivered on the next call. |
| `tool.result` | eagent | `call_id`, `name`, `output`, `is_error`, `images` | The outcome of one tool call. `images` are the pictures `view_image` brought back, copied under `<session>/attachments/`; they are shown to the model right after the result. A call left without a result by a restart gets one on resume (`interrupted: eagent restarted before this finished`). |
| `narrator.checks` | eagent | `count`, `usage`, `elapsed_ms`, `prompt_tokens`, `first_prompt`, `seen_seq`, `host`, `asked` | Totals for looks that ended in silence since the last such record, so their tokens count in the session's totals. `host` and `asked` name the route that served them, as on `assistant`: a look still out when the model changed is priced on the model that made it, and a look served by another route than the batch in hand starts a new record. A record without them (older logs) is priced on the route in use where it stands. A batch from a route that is no longer the one in use does not set the conversation's size. `prompt_tokens` is the size of the last of those prompts and `first_prompt` of the first (a resumed session reads how long its conversation was at its first call from the record, here or from the first `assistant`); `seen_seq` the newest event it had in view, so a resumed session does not look again at what was already weighed. Written after 20 such looks, before a look that acts, before a dossier, and at session end. |
| `answer.owed` | eagent | `seq`, `answer`, `tries`, `started` | What eagent still owes the user, as it stands after this change: `seq` is the oldest message kept for eagent that it looked at and left with no answer and nothing done (the reminders name it and every one kept since), or with `answer` the user's answer to its question that it held on; `seq` 0 says nothing is owed any more (answered, acted on, or given up after the last reminder). `tries` counts the reminder calls arranged, and `started` says reminder number `tries` has gone out. Written when a reminder is arranged, just before it goes out, and when the debt ends; never in a session whose model answers. A resumed session reads the newest one: a waiting reminder is due when it would have been, one that had gone out counts as made, so stopping and resuming does not start the reminders over. It renders nothing in eagent's conversation; an older reader ignores it. |
| `narrator.message` | eagent | `text`, `important` (buzz the phone), `attachments` (copied under `<session>/attachments/`), `auto`, `room` | Something eagent told the user. `auto` marks words the harness said without a model call: the outcome of a command the user typed, that the model cannot be reached, a closing report it had to write itself. `room` is on the notice that no restart can make room (it begins "My conversation is full again right after I restarted it"): the room for input (the window less the reply ceiling, in tokens) of the model it was found on. The decision stands on that model only while the room in force is no larger, so a run resumed with the window raised in the config asks afresh. A notice without it (older logs) stands on its model as before. |
| `narrator.question` | eagent | `id`, `text`, `options[]` | A question for the user, from `ask_user`. A new question replaces one still open. A batch session that ends with one open ends `awaiting-input` with exit code 2. |
| `harness.message` | eagent | `text` | A notice from the harness in eagent's conversation: no agent could be started, a turn stopped at the call limit with an agent still stuck on its screen, an autopilot idle check, an autopilot that reached its `until`. Wakes eagent. |
| `thread.title` | eagent, summarizer, or harness | `title`, `description`, `by`, `pin`, `seen_seq`, `usage`, `elapsed_ms`, `host`, `asked` | The session's title and summary, always of the whole session so far. Each replaces the previous; an empty field leaves that side unchanged. `by: summary` is the running summary: eagent's `update_thread` (actor `eagent`) or the dedicated summarizer's call (actor `summarizer`, with its `usage`, priced on the route `host` and `asked` name; without them, as in older logs or when its two calls were served by two routes, on the route in use). `by` absent with `pin` true is a name the user asked for. `by: finalechat` (actor `harness`) is what the app showed when the mirror attached. A pinned title is kept by later summaries. Mirrored to FinaleChat when the phone is on. |

### Relays

A relay is a coding agent (Claude Code, Codex, Antigravity, pi) that the session runs in a tmux (or screen) terminal eagent owns and passes the user's words to. The agent's own transcript (a Codex rollout, a Claude Code session file) is the source of these events; the terminal is typed into and read for dialogs. Every relay event is written by the harness.

| Type | Actor | Payload | Notes |
|---|---|---|---|
| `relay.start` | harness | `name`, `profile`, `agent` (`claude`, `codex`, `antigravity`, `pi`), `agent_label`, `label`, `dir`, `host` (`tmux` or `screen`), `target` (the terminal session, `eagent-relay-…`), `command`, `inner_id`, `transcript`, `resumed`, `model`, `effort` | Launched, or relaunched continuing the agent's own session. A start under the name of a relay that was never stopped (a restart, a model change), or one with `resumed`, continues that relay's history (turns, last report, sends, autopilot); any other start under a stopped relay's name is a new conversation and keeps only its usage limit. Either way, a send to the name recorded while the start was under way (held for it, and typed in once the agent is up) is the new agent's to confirm; after a stop it is also counted as the new agent's own send, which holds the name from that send on (what a later hand-over brief quotes as said to it). `model` and `effort` are the session's picks over the profile's (empty keeps the profile's, else the agent's own configuration). A resumed eagent reattaches to `target` instead of starting again. |
| `relay.inner` | harness | `name`, `inner_id`, `transcript` | The agent's own session id and transcript path, once found. Recorded again when the agent moves to another session of its own (pi's `/new`, `/resume`, `/fork`, or an extension's `ctx.newSession`): first as soon as the move is seen, with the new `inner_id` and an empty `transcript` (pi writes no file for a new session until its first prompt; a restart meanwhile opens the new session), then with the path once the file is found. What that session already held when pi opened it is history and is not reported; everything it writes after is, including a turn that finishes before eagent notices the move. |
| `relay.send` | harness | `name`, `id` (`r1`…), `from` (`user` or `eagent`), `seq` (the forwarded user message), `mode` (`queue`, `interrupt`, `after_turn`), `text`, `auto` | Text typed into the agent. `auto` marks a send made with no model call: a user message forwarded as it arrived, or one a typed command made. `from: eagent` sends are mirrored to the phone as typed. |
| `relay.moved` | harness | the fields of `relay.send` (`name` is the relay it goes to now, `id` unchanged), `prev` (the relay it was first sent to) | A send that waited for a switch, or was waiting to be typed when the switch stopped the old agent, goes to the agent that took over. From then on it is that relay's send: its arrival is confirmed under the new name, and the old relay stops waiting for it. Older sessions have none. |
| `relay.delivered` | harness | `name`, `id`, `ok`, `detail`, `outcome` | The transcript shows the text arrived, or (`ok` false) it did not. `outcome` says how sure a failure is: `not_sent` (nothing was typed, or the copy held for the end of the agent's turn was taken back unread) or `unconfirmed` (typed, or taken by Claude's hook, and its arrival never shown; this is also how a send still unconfirmed ends when its agent exits, is restarted (including a restart of a relay that was stopped) or is stopped (`relay_control` stop once what the stopped agent's terminal last read is on the record, its arrivals among it; Stop session, or a switch whose new agent could not start, with the `relay.end`; a stop while a start of that relay is under way settles it when that start ends; a switch that hands over settles eagent's own sends to the old agent once the new one has its brief, the user's being quoted in that brief)). A send held for the end of the agent's turn waits as long as that turn runs; once the turn is over and Claude's Stop hook has taken its file, or pi's extension has removed it (an interrupt put the message back in pi's editor), it gets the usual wait from then. One handed to Codex's or Antigravity's own queue waits while turns follow each other (that queue runs one message a turn); once a turn is over and no other has started a few seconds later, nothing will run it, and it gets the usual wait from then; one typed straight into the prompt (the agent idle, or the hand-over failed) gets the usual wait from its typing. The agent's own command (`/compact`), which shows no arrival, is `ok` once typed into the prompt or handed to Codex's or Antigravity's own queue; one held for Claude or pi is handed over as text and confirmed as any held message. A failure without `outcome` (older logs) reads as `unconfirmed`. A failure wakes eagent; `relay_forward` sends a user message again only when every earlier send of it to an agent under that relay name (any agent that held the name, including one stopped before) was `not_sent`. When the sends that were not `not_sent` (at least one) were all sent to the agent that held the name then before its stop and not passed on since (each arrived before that stop, or was never confirmed), and the agent holding it now started after that stop, the refusal says the message went to that earlier agent and that relay_send gives it to this one. The phone's receipt for a user message comes from all its sends: `delivered` if any arrived, else `sent` if any is on its way or `unconfirmed`, else `held`, and `failed` (the one receipt with a Retry) only when every send was `not_sent`. A `sent` message none of whose sends is still on its way and at least one `unconfirmed` is also named in the thread meta's `relay_unconfirmed`: it may not have arrived. One transcript entry confirms each send once. A resumed eagent takes the sends still unconfirmed (from their `relay.send` or `relay.moved`) to the reattached agent, which confirms them from its transcript or, after the usual wait, reports them `unconfirmed` without typing them again; for an agent that is gone, or that exits, they are reported `unconfirmed` where the exit is recorded. A reattach reads the last 4 MB of the transcript, or all of it when it has such sends, whose arrival may lie anywhere after they were recorded. A message held for the end of the turn that still waits in the spool, unclaimed, when its agent exits, is stopped (`relay_control` stop, Stop session, a switch), or is started again (taken back before the new launch clears the spool), is taken back and is `not_sent`: nothing took it. |
| `relay.state` | harness | `name`, `state` (`starting`, `working`, `idle`, `blocked`, `exited`), `detail`, `dialog` | `blocked`: a dialog on the screen (or one pi reports itself), not ready 25 s after starting, or no transcript activity for 10 minutes while working. `dialog`, on `blocked`, is the title of a dialog the agent reports itself (pi's extension), and only then; older records have none. A `relay.progress` does not clear `blocked` (pi still writes under a dialog it reports, and says working itself when the dialog ends); the next `relay.state` does, and a `relay.turn` does unless the blocked state names a `dialog` (the turn is counted and the relay stays blocked until the seat says the dialog is over; in records written before `dialog`, the turn makes it idle, as it always did). A model or effort change does not start the agent again while a dialog it reports holds it (its terminal says so, as `dialog` on the blocked `relay.state` does), whatever the record shows: it waits, and applies once the terminal says it is idle. An agent blocked for a slow start or for no transcript activity is started again with the change at once. A change, asked now or waiting for a turn's end, does not start the agent again while a send to the agent is still on its way (a message held for that turn's end, one in its own queue, one typed and not yet shown arriving): the agent reads it next and starts a turn, and the change applies when that turn ends, or when the send's outcome is recorded without its arrival while the agent is idle. `exited` also records an agent that was stopped to start again and could not start. `blocked` and `exited` wake eagent. |
| `relay.progress` | harness | `name`, `text` | Something the agent said mid-turn. Shown in eagent's conversation; a progress look weighs it. |
| `relay.turn` | harness | `name`, `text` (the agent's final message), `duration_ms`, `tools`, `images`, `interrupted`, `idle` | Wakes eagent with the agent's report. `idle` marks a turn that answered a message eagent sent without running any tools, and adds a reminder that an agent waiting on its own work should not be sent another message. |
| `relay.limit` | harness | `name`, `used_percent`, `window`, `resets_at`, `text`, `exhausted` | The agent's usage budget crossed 50, 80, 95 or 100%, or a limit message appeared. Wakes eagent. |
| `relay.autopilot` | harness | `name`, `instruction`, `until` (RFC3339, empty for "until the user says stop"), `decide`, `off` | A standing order to keep the agent going, set with `relay_autopilot` or `/autopilot`. The steer of every wake that asks eagent to act restates it. While the agent sits idle after a turn with nothing sent to it since, the harness wakes eagent every 10 minutes to look (a `harness.message`). When `until` passes the harness writes `off` and tells eagent to report. |
| `relay.read` | harness | `name`, `read` | How far the agent's transcript was read, after a read whose only news was a user line that confirmed nothing (a copy of a queued message, words typed in its terminal). `relay.delivered`, `relay.state`, `relay.progress`, `relay.turn` and `relay.limit` that a line of the transcript gave carry `read` too: the end of that line. A reattach to the transcript the newest of them was read in reads on from there (what starts before it is history, what follows news, whenever it was written); without one (records written before `read`, or after the agent moved to another transcript) it cuts by the relay's last event time, as before. Not shown in eagent's conversation. |
| `relay.end` | harness | `name`, `reason` | Stopped on purpose, or handed over to another profile. A batch session stays up while any relay is active. A switch writes its `relay.end` (`handed over to …`), the new relay's `relay.start` and the handoff brief (a `relay.send` from `eagent`) as neighbouring events; a switch away from an agent that brief started and that has finished no turn since reads them to hand over from the agent before it (told the work unless the brief was `not_sent`), in this run or a resumed one. |

### Runtime settings

These are written by `internal/harness/settings.go` with the type strings below; they have no payload struct in `internal/event`.

| Type | Actor | Payload | Notes |
|---|---|---|---|

| `settings.changed` | harness | `format`, `command_id`, `user_id`, `proposal_sha256`, `generation`, `resource_key`, `previous`, `values`, `result` | A settings change from the app, recorded before it is applied and acknowledged. A changed route also writes a `route` event. |

| `inbox.taken` | harness | `inbox` (as on `user.message`), `text` (the command as written; absent in records from before it) | One of eagent's own commands came in that `<session>/inbox/` file, and is carried out next; it is written before the file is removed. ### Diagnostics and the phone

| Type | Actor | Payload | Notes |
|---|---|---|---|
| `route` | harness | `actor` (`eagent` or `summarizer`), `provider`, `base_url`, `model`, `reason` | A fallback route took over, or a settings change picked another route. The reducer updates the actor's model and endpoint; the phone's model chip follows eagent's. |
| `phone.question` | harness | `question_id`, `card_id`, `thread_id`, `key` | A question was posted to the phone as a card, so a later run can withdraw the card when the question is answered elsewhere. `thread_id` and `key` (the number of the card's client key) let a later ask of the question start where its cards in that thread left off. `key` is absent for a card made with no client key (a service without idempotency); a later ask of the question makes a new card and withdraws every such earlier one (one already dismissed counts as the user's dismissal). Any the service did not let be withdrawn may still be open, and a resume checks each. With an empty `card_id`, the service refused the question as a card and it went to `thread_id` as a message: on a service without client keys a later ask of the question does not post it there again (a message stays; with client keys the post's own key does the same), and a later run that settles the question elsewhere tells the thread so, a message not being withdrawable as a card is. |
| `phone.read` | harness | `message_id` | The session took in that app message, and no `user.message` or `user.answer` names it (it was a command, empty, all its files refused, or an answer whose card was already taken). For a command it is written before the command runs; a command that came while the session was ending is written and not run (the thread is told so), unless a message before it was left for the next run. Every mirror also writes one when it starts, naming the message its poll reads on from: the cursor. A run resumed with no app message and no cursor to go on after reads on from just before the earliest message that waited, judged by time as below; `message_id` is then empty when that message is the user's first in the thread. While the thread cannot be read for that it is tried again; a read that fails for good writes no cursor, so none is recorded past messages nobody read; the poll then reads on from the session's own post, and the session's log and the thread say that what was sent while it was stopped was not read. With `phone_id` on `user.message` and `user.answer`, the newest of these says where a resumed session goes on reading the thread, so a message sent while it was stopped is taken once and never skipped. Whether a run keeps this ledger is said by `phone_ledger` on its `session.start` or `session.resume`, not by these. After a run without it, the ledger starts afresh with the next run that has it: messages from before that run are judged by time. |
| `phone.answer_taken` | harness | `card_id` | The answer written on that phone card reached the session (as the answer, or as a message). The message poll and a re-ask of the question leave the card's answer alone from then on, in this run and later ones. |
| `phone.mirror` | harness | `seq`, `message_id` | A user message written at the terminal or in the web UI (`seq`) was copied to the phone thread as `message_id`, so a later run keeps the receipt under it. |
| `images.refused` | harness | `paths` | A provider refused these pictures during a call (undecodable, or over a limit of its own that the file does not show), and the call went through without them. `paths` are the copies kept in the session. From here on the conversation is rendered with a note in place of each, whichever process or route renders it, so the picture is not uploaded again and the request stays the same after a resume. |
| `phone.thread` | harness | `thread_id`, `external_id`, `base_url`, `remote_mode` | The session is mirrored to the user's phone through FinaleChat; `external_id` is `eagent:<session>`. ## eagent's conversation

eagent's model reads one conversation, rendered from the log by `state.View`
(`internal/state/views.go`) for every call. The rendering depends only on the
log, so each call's conversation extends the one before it and provider
prompt caches keep hitting.

- **Which events.** In a session's first subsession, its own file. After a rollover, the `dossier` as the first message (a `[Briefing…]` header and its text), then every event after its `covers_seq`, including events written to the previous file while the dossier was being composed. With `covers_none` that is the whole record. A dossier with neither field (an older log) is followed by its own file only.
- **eagent's own turns.** Each `assistant` event is an assistant message with its tool calls, followed by their `tool.result`s; a call with no result reads as interrupted. A result belongs to the reply it follows in the log, and two calls of one reply with the same id take its results in order: an id alone does not say which call, because some providers use the same ids in every response. Pictures from `view_image` follow as a user message. Events that arrived while a call was in flight (after its `seen_seq`) are placed after that call's results, which is when the model first saw them. A `steer` renders as the user message it was, right before the reply it led to.
- **What the user wrote.** Each `user.message` renders through the `USER_MESSAGE.md` template as an IRC-style line, `[2006-01-02 15:04:05] <nick> text` (nick from `source`: the terminal is `user`, `web` is `user@web`, `finalechat` is `user@phone`), with a note on any attachments, the client capsule as a trailing `[client line]` when the event has one, and `[Not passed to the agent: <held>.]` when it was held. Each `user.answer` renders through `USER_ANSWER.md` the same way, with the answered question's id, and the question's text when it was asked before the current briefing. Pictures the user sent in common formats go with the message. Timestamps come from the event's own time in the session's `tz`. Both templates can be overridden in `.agents/eagent/prompts/` like every other prompt.
- **Notices.** One user message each for: a `user.dismiss`; a `harness.message`; a `schedule.fire` (with its note); an `auto` `narrator.message`; a `session.resume`; an `error`; a `route` for eagent; a `phone.thread` whose `remote_mode` changed; and the relay events (`relay.start`, `relay.end`, `relay.progress`, `relay.turn` with its report clipped to `report_max_chars`, `relay.limit`, `relay.autopilot`, `relay.state` when `blocked` or `exited`, `relay.delivered` when not `ok`, `relay.send` when `auto`, and `relay.moved`). Other events add nothing.
- **The tail.** After the conversation each call gets the tail (`internal/harness/tail.go`) as one more user message. It is recorded as a `steer` only when the model acts on that look; when it holds, nothing is recorded but a count in `narrator.checks`, and the next call starts from the same bytes.

`eagent show <id>` prints a readable transcript; `--raw` prints every event with its `file:line`, and `--actor eagent` (or `user`, `harness`) one actor's events. `eagent replay <id>` reports the state rebuilt from the log and how many messages eagent's conversation has.

## Events in older logs

Logs written when eagent ran three models still list, show, export, replay and resume. Nothing writes these any more (`internal/event/legacy.go`).

| Actor or type | What it was | How it is treated now |
|---|---|---|
| `orchestrator` | The model that decided and could do the work itself. | Its `assistant`, `tool.result`, `steer` and `harness.message` events are not rendered in eagent's conversation. Its model shows in `eagent show` and in the usage totals; its last prompt size stands in for the context size. |
| `task` | Task workers, with `task` set on their events. | Their events are not rendered in eagent's conversation. `eagent show --actor task --task t3` still prints one worker's events. Their `cwd.change` events are ignored. |
| `narrator` | The model that spoke to the user. | `eagent show` prints its `narrator.message` and `narrator.question` events as eagent's; the dossier index lists them as what the user was told and asked. Summary calls made on its route were written as `thread.title` by the harness, and their usage counts as the narrator's. |
| `task.create`, `task.start`, `task.end` | A task's lifecycle. | `eagent show` prints `task.create` (as `delegate`) and `task.end`; the dossier index lists `task.end`. |
| `note` | A hint from the orchestrator to the narrator. | Printed by `eagent show`; listed in the dossier index. |
| `yield` | The orchestrator had nothing to do (`done` ended a batch session). | Printed by `eagent show` as `DONE` or `waiting`; listed in the dossier index and in the fallback briefing. |
| `proc.start`, `proc.pid`, `proc.exit` | Shell commands the orchestrator and workers ran. | History only: shown by `eagent show --raw`. No process is tracked or stopped on resume. |
| `narrator.trim` | Moved the start of the narrator's view to keep its prompt short. | History only. |
| `cwd.change` from an orchestrator | Every `cd` an actor's shell made. | Only the latest path counts, as the session's folder. |
| `dossier` with `task_id` | A briefing written by a task worker. | Read like any dossier; `by` is absent. |

On resume, a log from the three-actor design with no `eagent` calls is not owed any looks. Before anything else the loop writes a dossier from the record's files, with a map over every old file and the old dossiers included, and opens a new subsession (`reason: upgrade`) with it, so eagent's conversation never has to render the old events. If the model cannot write that dossier, the harness assembles one from what the user was last told, how the old session left things, each agent's last report and the old session's last briefing. `session_search` and `session_read` reach the whole record, old files included. `eagent replay` notes that such a log's tasks and processes are history only.
